# BUG-002 — Server accepts a checkout with no address, delivery method or payment

**Reported by:** Carina
**Date:** 2026-10-20
**Component:** Checkout — POST /rest/basket/&lt;basketId&gt;/checkout
**Environment:** OWASP Juice Shop 20.2.0 (Docker image bkimminich/juice-shop),
reproduced at the API level
**Severity:** Major
**Priority:** High

## Preconditions
- A registered, logged-in user (auth token available).
- The user's basket contains 1 × Apple Juice (1000ml).
- No address, delivery method or payment has been selected.

## Steps to reproduce
1. Log in: `POST /rest/user/login` with the user's email and password. Note the
   `token` and `bid` (basket id) in the response.
2. Send `POST /rest/basket/<bid>/checkout` with header
   `Authorization: Bearer <token>` and body:
   `{"couponData":"bnVsbA==","orderDetails":{}}`
3. Request `GET /rest/order-history` with the same token.

## Expected result
The checkout is rejected (4xx) with a message saying an address, delivery
method and payment are required. No order is created.

## Actual result
- Step 2 returns **HTTP 200** with
  `{"orderConfirmation":"9834-668e5141d037eca4"}`.
- The basket is emptied.
- Step 3 lists the order with `"delivered":false` and `"deliveryPrice":0` —
  an order with no delivery address and no payment method.

The same happens with an empty request body (`{}`): HTTP 200 and an order
confirmation.

## Reproducibility
Reproduced on 2 separate fresh accounts (empty `orderDetails`, and empty body).

## Notes / impact
The checkout screens lead users through address → delivery → payment, but
the server does not require any of them. Anyone sending the request directly
(or a broken client) can create orders that cannot be delivered or charged.
Related: BUG-003.

**Oracle:** Purpose — an order exists to be delivered and paid for; one with
no address or payment can't fulfil that purpose.
